# 时间线为什么断断续续（一次真机复盘的完整结论）

> 起因（用户 2026-09-27 的提问）：设置窗口「今天在做什么（时间线）」里出现
> `10:58–11:01 聊天（元宝）· 2 分钟`、`11:03–11:05 聊天（元宝）· 2 分钟`、
> `13:11–13:11 浏览网页（msedge）· 不到 1 分钟`、`13:15–13:16 浏览网页（Microsoft Edge）· 1 分钟`
> 这样的碎片，中间还有 11:13 → 13:11 的两小时空洞，而且同一个 Edge 出现了三个名字。
>
> 这份文档把**当天真实数据**摊开，逐条对上原因，并记录已经落地的修法与口径。
> 所有数字都可在本机复现（命令见文末）。
>
> **这一轮的结论（已实现）**：
> 1. 根因是**推理模型把 `max_tokens` 花在思考上** → 视觉采样约 1/3 直接失败 → 时间线出现空洞；
>    现在视觉/短输出一律关推理，并在空内容时自动加大预算重试一次；
> 2. 合并阈值 90 → **150 秒**，并且**同一个进程**内的"没认出来"会被桥接（不切段、次数留痕）；
> 3. **模型复核间隔**（默认 5 分钟 + 换了应用立刻复核）把视觉调用从"每 30 秒一次"
>    降到"每 5 分钟一次"，中间的采样沿用上一次判断 —— 时间线不再因为省钱而断裂；
> 4. 同一个程序永远同一个显示名（`msedge` → `Microsoft Edge`）。

## 1. 数据从哪来（先明确"应该是什么样"）

```text
perception-service.tick()           每 30 秒一次（captureIntervalMs，默认 30000）
      │  ① 要不要花一次模型调用？换了应用 → 是；否则距上次 ≥ modelRefreshMs(5 分钟) → 是；
      │     都不是 → **沿用上一次的模型判断**（不花钱，仍然记一条观察）
      │  ② 要调用时：截图 + 窗口上下文 → 视觉模型 → ScreenObservation{at, scene, app, appLabel, …}
      ▼
store.recordObservation()          追加进 data/perception/observations-<日期>.jsonl（每条都写）
      ▼
timeline.observe() → appendObservation()
      │  · scene 是"没认出来"（other）：同一进程且间隔 ≤ 阈值 → **桥接**（延长上一段、次数留痕）；
      │    否则不写时间线、也不打断上一段
      │  · 与上一段 scene 相同 且 间隔 ≤ SEGMENT_GAP_MS(150s) → 延长上一段
      │  · 否则 → 上一段补到这一刻并另起一段（间隔 > 150s 则留白，进 unaccountedMinutes）
      ▼
data/perception/timeline-<日期>.json  →  设置面板「今天在做什么」逐行显示
```

所以"连贯"的前提是三条同时成立：**采样没失败**、**场景认出来了（或被桥接）**、
**两次认出来的间隔 ≤ 150 秒**。

## 3. 五个原因（按影响排序）

### 3.1 根因（已修）：推理模型把 `max_tokens` 吃光了

配置是 `https://api.deepseek.com` + `deepseek-flash` + `maxTokens: 220`，
而 `analyzeScene()` 那条请求只给 `max_tokens: 360`。
`deepseek-flash` 是**推理模型**：每次回答前先写 600~1000 字 reasoning。
实测（`build/vision-probe.mjs`，同一张图连打多次）：

| 次数 | finish_reason | content | reasoning | completion_tokens |
|---|---|---|---|---|
| #1 | **length** | 193 字（**被截断在字符串中间**） | 1046 字 | 360（其中推理 290） |
| #2 | stop | 235 字 | 583 字 | 234（推理 138） |
| #3 | stop | 221 字 | 1039 字 | 339（推理 248） |

后果有**两种**，都表现为时间线断裂：

- 截断在 JSON 中间 → `parseJsonObject()` 失败 → 这条观察退化成"没认出来"（scene=other）→ 不进时间线；
- 推理把 360 token 全部用光 → `content` 为空 → `LLMError('EMPTY')` → **这条观察根本不存在**。

真机会话日志（`%APPDATA%\DesktopPet\logs\desktop-pet.log`）里直接看得到：
`[Perception] scene analysis failed | 模型返回了空内容`，在 13:49–13:53 的 10 次采样里出现了 **3 次**；
更早的一次会话里是 3 次成功 / 3 次空内容。

**修法（已实现）**：

1. 视觉/短输出调用一律带 `reasoning_effort: 'none'`（关推理）——
   实测同一张图 completion 从 169~341 token 降到 **53~57**、延迟从 1.6~2.4s 降到 **0.75s**，JSON 更完整；
2. `LLMClient.complete()` 在**空内容**时自动把 `max_tokens` 放大到 3 倍（至少 900）**重试一次**；
   服务商不认 `reasoning_effort`（400/404）时也会去掉该字段重试一次；
3. 视觉那条在 JSON 解析失败时**加预算再要一次**（1400 token），避免丢掉一整条观察；
4. 空内容的错误文案现在会写明 `finish_reason` 与推理 token
   （"max_tokens 被推理过程用光" vs "模型就是没答"是两种完全不同的修法）。

### 3.2 "没认出来"的那条会被整条丢掉（已改为"同进程桥接"）

需求是"没认出来就当作没看见"，所以 `other` 观察**不写进时间线、也不作为依据**。
它带来一个副作用：**夹在中间的每一次"没认出来"都占掉一个 30 秒槽位**，
两次认出来之间的间隔就被推大，超过合并阈值就断成两段 ——
这就是 11:01→11:03、11:05→11:11 那几处碎片。

**修法（已实现，用户选定的口径）**：**同一个进程**内桥接。

- `other` 观察的 `app`（进程名，本地确定性证据）与上一段一致，且距上一段结束 ≤ 阈值
  → 把上一段的 `end` 推到这一刻，`samples + 1`，并记一条 `unrecognizedSamples`；
- 换了应用、或者中间真的断了采样 → 不桥接（那段空白如实留给 `unaccountedMinutes`）；
- 面板那一行会写"（其中 N 次没认出来）"——**这段时长里有多少是推断是可追问的**，
  不是把不知道的事悄悄算成知道。

### 3.3 合并阈值 90 秒 vs 采样节拍 30 秒（已放宽到 150 秒）

原来 `SEGMENT_GAP_MS = 90000`：

- 漏 1 次采样（60s）→ 仍合并；
- 漏 2 次（90s）→ 边界值，仍合并；
- 漏 3 次（120s）→ 断段；
- **中间夹一次 `other`（间隔 119s）→ 断段。**

现在 `SEGMENT_GAP_MS = 150000`（5 个采样槽位）：

- 漏 1~2 次采样（60s / 90s）→ 合并；
- **夹一次 `other`（119s）→ 合并**（用户看到的那三行碎片正是这样来的）；
- 漏 5 次以上（≥180s）、或真实空档 4 分钟 → 仍然断段。

代价是"最长 2.5 分钟的真实空档会被算进上一段"（换段补时规则会把它补到下一个观察时刻）——
`unaccountedMinutes` 因此变小（同一条真机数据：8 分钟 vs 原来的 15.5）。
这是口径变化：面板上的"在电脑前"从此包含最多 2.5 分钟的"其实没采到样"，
而同一进程内的"没认出来"另有次数留痕。

### 3.4 程序没在跑的时候没有采样

11:13:35 → 13:11:19（约 2 小时）整段没有任何日志行，说明桌宠当时没在运行 ——
面板上就是一段空白。这不是丢数据，是"那段时间没人记录"。

### 3.5 时长是取整的分钟数

`formatDuration()` 用 `Math.round()`：`10:58:35–11:01:05` 实际 2 分 30 秒 → 显示"2 分钟"；
不足 1 分钟的显示"不到 1 分钟"。所以"2 分钟"看起来像少了 30 秒，其实只是取整。

## 4. 顺带修掉的一个显示缺陷：同一个 Edge 有三个名字

| 时间 | 面板显示 | 数据里的字段 |
|---|---|---|
| 13:11 | `msedge` | `app='msedge'`，`appLabel=''` |
| 13:15/13:18 | `Microsoft Edge` | `app='msedge'`，`appLabel='Microsoft Edge'` |
| 13:19/13:23 | `Edge` | `app='msedge'`，`appLabel='Edge'` |

原因：`app` 是**进程名**（稳定身份，13:11 之后才改成这样），`appLabel` 是**模型读出来的友好名**
（自由文本，同一程序可能写成三种）；而显示层原来"友好名优先"，于是同一个程序显示成三个名字。

**修法（已实现）**：新增 `appDisplayName(app, appLabel)` ——
**已知进程名一律用固定名字**（`msedge → Microsoft Edge`、`code → VS Code`、`typora → Typora`…），
表里没有的（小众软件）才回退到模型给的名字，最后回退到进程名。
时间线面板、`formatSegmentLine()`、`formatTimelineText()`（喂聊天/日记的那段文本）**共用同一个函数**，
所以三处口径一致。日志行仍保留两个名字（`浏览网页（Microsoft Edge / msedge）`），
因为复盘时"她以为在用什么"与"到底是哪个程序"是两件事。

## 5. 已落地的两个口径（用户 2026-09-27 选定）

### 5.1 模型复核间隔：只在"换了应用 / 到点"时才花 token

真机每次视觉调用约 **1450~1700 token**（系统提示词 + 整屏图 + 地址栏图 + 窗口列表）。
按 30 秒一次计算：

```text
每小时 ≈ 120 次 × 1500 token ≈ 180,000 token
预算 budget = 200,000 token / 天   →  约 **1 小时** 用完
```

预算耗尽后她退回本地降级（只看窗口进程名，描述变粗），聊天也跟着受影响 ——
用户看到的是"她怎么越来越笨"。选定方案是**只在窗口变化或每 5 分钟才调模型**：

| | 行为 | 花多少 |
|---|---|---|
| 换了应用 | **立刻**调模型重新判断 | 1 次 |
| 同一个应用满 5 分钟 | 兜底复核一次 | 1 次 |
| 其余每 30 秒 | **沿用上一次的模型判断**（`mode: 'local'`、`tokens: 0`），照样记一条观察 | **0** |

于是：时间线仍然是 30 秒颗粒度、不断段，而视觉调用从 **120 次/小时** 降到
**≤12 次/小时**（约 18,000 token/小时）—— 同一份预算从"1 小时"变成"一整天还富余"。

实现要点（`perception-service.tick()`）：

- 判据是**前台进程名**（`effectiveForeground()` + `normalizeProcessName`），不是窗口标题 ——
  标题在浏览器里几十秒就变一次，用它当判据等于没省；
- 复用的是**上一次的模型判断**，不是"重新用本地规则猜一遍"：
  同一个窗口里模型说"写东西"、进程名规则猜"浏览网页"，两个判断来回横跳只会
  让时间线因为场景反复变化而更碎（正好是这次要修的问题）；
- 复用的观察带 `evidence`（"窗口未变化，沿用上一次的判断"），复盘时不会误以为是新看到的；
- 复用的观察 `mode: 'local'` → `decide()` 不会拿它去主动开口（本地信号不配开口），
  但它**照样进习惯统计与时间线**；
- 可在设置 →「采样与频率」→「模型复核间隔（毫秒）」调整（默认 300000；调到采样间隔就是"每次都调模型"）。

> 为什么"换了应用立刻看"很重要：场景变化打招呼、习惯预测、日记都依赖**场景真的变了**
> 这件事。进程名是本地确定性证据，拿它当触发器既便宜又不漏。

### 5.2 断段口径：150 秒 + 同进程桥接

见 §3.2 / §3.3。两种"看起来像丢数据"的情况现在分得很清楚：

| 情况 | 现在的行为 |
|---|---|
| 同一个应用里模型几次没认出来 | **不断段**，次数记在 `unrecognizedSamples`，面板显示"其中 N 次没认出来" |
| 换了应用、或者真的没采到样（≥150 秒空档） | 断段，空白进 `unaccountedMinutes`（面板"没认出来/没采样"） |

> 反直觉的一点：采样变慢**不会**让时间线更碎 —— 碎片来自"两次认出来的间隔"，
> 而 150 秒阈值对 60 秒节拍仍然成立；真正让阈值吃紧的是"模型失败率"，
> 那已经在 §3.1 修掉了。

## 6. 怎么复现这些结论

```powershell
# 1) 时间线为什么断：把观察与区间摊开对照（一次性分析脚本）
node build/analyze-timeline.cjs 2026-09-27 10:50 13:30

# 2) 模型是不是"看得见图 + 推理吃掉了预算"（会真的调用你配置的端点，花费极小）
node build/vision-probe.mjs     # 复现 finish_reason=length / content 被截断
node build/vision-probe2.mjs    # 对比 reasoning_effort=none 前后的 token 与延迟

# 3) 运行期日志（中文唯一可靠出口，UTF-8 写入）
npm run logs -- --tail 80       # 看 scene analysis failed / llm completion ok（含 finish= 与 reasoningTokens=）
```

> `build/analyze-timeline.cjs`、`build/vision-probe*.mjs` 是**一次性诊断脚本**（放在 `build/`，
> 不属于产品代码，也不会被打包）。密钥只从 `data/ai-settings.json` 读取，脚本从不打印它。
