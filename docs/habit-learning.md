# 用户习惯学习机制（她学什么、怎么学、用在哪）

这份文档回答一个问题：**这只桌宠到底"学会"了你的什么，以及她是怎么用出来的。**

- 行号基准：`308 项验收通过` 的那一版（心情过低换池、小纸条可删可看之后）。
  定位请以**符号名**为准，行号只作辅助。
- 与另外两份文档的关系：
  - `docs/memory.md` 讲**记忆**（她记住了哪些内容、存在哪、保留多久）；
  - `docs/animation-triggers.md` 讲**动画**（每条动画由什么触发）；
  - **本文**讲**习惯**：把"你什么时候在做什么"变成可解释的统计，并从"你理不理她"里学说话时机。
- 事实来源：代码 + `build/acceptance.json` + `tools/probe-*.cjs` 的真机输出。

---

## 0. 一句话总结

她没有黑盒模型式的"用户画像"，而是**五层可解释的统计**，每一层都能用一句话说清楚、
且都停在"用户看得懂"的粒度上：

| 层 | 一句话 |
| --- | --- |
| L1 场景画像 | `10 点你通常在写代码`（按小时直方图） |
| L2 行为信号 | `你已经连续 2 小时没起来了` / `现在 3 点，你还没睡` |
| L3 长期事实 | `你一般 1 点睡` / `你在写论文`（从你说过的话里抽） |
| L4 反馈策略 | `写代码时我开口 3 次你都没理我，那我少说点` |
| L5 经历与时间线 | `今天你写代码花了 2 小时 22 分` / `常常在写代码` |

L1 / L2 / L5 来自**感知**（看屏幕、看空闲时间），L3 来自**对话**，
L4 来自**她自己的开口有没有被回应**——三条完全不同的输入，最后都汇进同一个"她怎么表现"。

> 设计取向（写在 `learnHabit()` 的注释里）：需求里提到的强化学习 / Contextual Bandit 属于
> "要做成推荐系统"的路径，**当前版本刻意停在可解释的统计模型上** ——
> 用户能看懂"她学会了我 10 点在写代码"，也才敢让它影响行为。

## 1. 一张总表：五层分别学什么

| # | 层 | 学什么 | 数据落盘 | 更新时机 | 最小样本门槛 | 谁读它 |
|---|---|---|---|---|---|---|
| L1 | **场景画像** | `平日/周末 × 小时 -> 场景 -> 天数`（按天去重 + 每天衰减） | `perception/habits.json`（v2） | 每次**认出来的**观察（默认 30s 一次） | 该小时 ≥**3 天**、其中主场景 ≥**2 天** | 闲聊的"习惯询问"、设置面板的"这个点通常"、**L6 习惯模型**、宫殿的习惯节点（看总采样数） |
| L2 | **行为信号** | 空闲秒数 / 连续使用分钟 / 一小时切换次数 / 深夜 | **不落盘**（纯推导） | 每次采样 + 电源/锁屏事件 | 无（实时值） | 频率闸门、久坐提醒、深夜提醒、反思素材 |
| L3 | **长期事实** | `routine`（作息）、`interest`、`activity`、`project`、`preference`、`relation`、`name`、`note` | `memory/profile.json` | 每轮对话后（规则）+ 每 6 轮（模型整理） | 置信度阈值（规则 0.55–0.8） | 聊天 / 日记 / 小纸条的提示词 |
| L4 | **反馈策略** | `哪个场景下我开口有没有被回应` | `reflection/feedback-*.jsonl` → `policy.json` | 每次主动开口 + 每天反思一次 | ≥3 次且回应率 ≤1/3（或 ≥5 次且 ≥0.8） | **感知的频率闸门**（唯一会改行为的一层） |
| L5 | **经历与时间线** | 今天在做什么 / "常常在写代码" | `perception/timeline-*.json`、`daily-*.md`、`memory/nodes.json` | 每次观察累积 + 每天叙事 | 合段间隔 150s（同进程内"没认出来"可桥接）；习惯节点需采样 ≥20 且某场景 ≥10 | 闲聊的"今天的活动"/"最近的事"、日记、聊天提示词 |
| L6 | **习惯模型** | 把 L1 的统计**归纳成一段话**（"她眼里的你"） | `perception/habit-model.json` | 每天 `habitModelHour`（默认 22 点）后一次；也可手动「立刻建模」 | 至少要有可归纳的数据（否则说"还没摸清"） | 设置面板、闲聊里那句"这个点你一般在写代码吧？" |

四条**刻意的边界**（下面 §5 详细展开）：不猜、没认出来当作没看见、策略只能收紧、
**模型只写措辞不写事实**（L6）。

## 2. 逐层细节

### 2.1 L1 场景画像：`10 点你通常在写代码`

**形状**（`shared/perception-types.ts` 的 `HabitProfile`，**v2**）：

```jsonc
{
  "version": 2,
  // 桶 key 是 "<weekday|weekend|*>|<小时>"，值是**看到它的日期**（升序去重）
  "seen": {
    "weekday|10": { "coding": ["2026-09-24", "2026-09-25", "2026-09-26"] },
    "weekend|10": { "reading": ["2026-09-20"] },
    "*|14": { "browsing": ["2026-09-18", "2026-09-19"] }   // ← v1 迁移过来的旧数据
  },
  "apps": { "weekday|10": { "Code": ["2026-09-24", "2026-09-25", "2026-09-26"] } },
  "daily": { "2026-09-26": { "earliestHour": 9, "latestHour": 23 } },  // 最近 21 天
  "observedHours": 6,          // 有数据的小时数（不分平日周末去重）
  "samples": 412,              // 观察总数（展示用；**不是**直方图的单位）
  "activeDays": 15,            // 历史累计活跃天数
  "latestActiveHour": 22,      // `daily` 里 latestHour 的**中位数**（会回落）
  "earliestActiveHour": 9,     // earliestHour 的中位数
  "lastActiveDate": "2026-09-26",
  "updatedAt": "2026-09-26T14:03:00.000Z"
}
```

> **天数 = 日期数组的长度**（`habitCounts()` 负责取，别自己 `.length`）。
> 为什么存日期而不是存一个"衰减后的权重"：先做过指数衰减（×0.95/天），
> 结果"连续 3 天"的权重只有 **2.85** —— 任何按"天"表达的门槛都会被它搞错，
> 而且小数天数没法向用户解释。日期数组则是精确的整数，**遗忘就是窗口滑动**。

**学习规则**（`learnHabit()`，**纯函数**，返回新 profile），顺序不能乱：

| 步骤 | 处理 |
|---|---|
| 0. 过滤 | `idle` / `sensitive` / 没认出来（`other`）**跳过**：前两个不是"在做事"，最后一个见 §5.2 |
| 1. 剪窗口（遗忘） | 只保留最近 `HABIT_WINDOW_DAYS`（默认 **21**）个**运行过的日子**；超出的最早那些日期丢掉，表空了就把整条 key 删掉。**没启动程序的日子不占名额** —— 出差一周回来，学到的东西一点都不会少 |
| 2. 按天去重 | 同一天、同一小时、同一场景只加**一个日期** —— 盯着一格看两小时也刷不成铁证 |
| 3. 分档 | 桶 key 带 `habitDayKindOf()`（周六日 = `weekend`，其余 = `weekday`） |
| 4. 记应用 | `apps[桶][应用名]` 也追加日期（同样按天去重） |
| 5. 作息窗口 | 更新 `daily[dateKey]` 的 earliest/latest（同一天取更宽的那个）；再由**中位数**重算 `earliest/latestActiveHour` |

**读取**（`describeHour()`）：先查当前档（weekday/weekend），没有再退回 `*` 档（v1 旧数据）；
不指定档位时把三档**合并**看（"这个小时总的来说在做什么"）。
该小时总天数 ≥ **3**、主场景 ≥ **2** 天才返回结论，否则 `null`（**样本不够就不装懂**）。
`allowAnyFallback: false` 可以关掉 `*` 兜底 —— 面板、习惯条目、给模型的统计文本都用它，
免得旧数据被同时算成"工作日"和"周末"两份证据（实测出现过两两重复的条目）。
`topSceneAtHour()` 是它的旧签名封装（只回答场景）。

**台词生成**（`habitPredictionText()`）按顺序判三件事：

1. **深夜对比**：`behavior.lateNight` 且 `latestActiveHour` 存在，且
   `当前小时 - latestActiveHour >= 2` → `今天已经比你平时睡觉的时间晚 N 个小时了……`
   （这是 3.6 的原始例子，也是最有效的一句；因为用的是中位数，作息改了它会跟着回落）；
2. 该小时没有足够的已识别场景 → `null`（不说话）；
3. 否则 → `按你平时的习惯，这个点一般在写代码（Code），今天也是吗？`
   —— 应用名（`Code`）只在**它也攒够天数**时才带上。

**观测来源有三条路**（都进同一份画像，精度不同）：

| 路径 | 什么时候走 | 得到什么 | 调模型？ |
|---|---|---|---|
| 视觉模型 | 配了密钥且能截图 | 场景 + 应用 + 活动描述 + 聚焦度 | 是（一次多模态请求） |
| **终端短路** | 最上层窗口是终端类进程 | 固定结论 `terminal`（不读缓冲区、不截图） | **否** |
| 本地降级 | 没配密钥 / 模型不可用 | 只凭进程名 + 标题猜（`Code` → `coding`、标题带 `.pdf` → `reading`） | **否** |

本地降级**只记录、不主动开口**（`decide()` 只接受 `mode === 'llm'` 的观察）——
因为"标题里有 Code 就当写代码"猜错了会冒出一句莫名其妙的话。

> ⚠️ 采样本身会不会"漏"直接决定这三条路的产出密度：推理模型在 `max_tokens`
> 太小时会**先写几百字思考、正文一个字都不剩**，那一次采样就什么都不记录
> （「今天在做什么」因此断裂）。根因、真机数据与修法见
> [`timeline-continuity.md`](timeline-continuity.md)。

**v1 → v2 迁移**（`migrateHabitProfile()`，**纯函数**，放在 shared 层所以验收能直接喂 JSON 断言）：

| 问题 | 处理 |
|---|---|
| 旧值单位是"观察次数" | 按 `min(次数, 活跃天数)` 截断 —— 27 次观察分布在 3 个活跃日里，最多就是 3 天 |
| v2 存的是日期，v1 没有日期 | 从 `lastActiveDate` **往前一天一个**合成同样多的日期 |
| 不知道旧数据那天是星期几 | 全部装进 `*`（不分平日周末）这一档，读取时兜底 |
| 旧的 `latest/earliestActiveHour` 是历史极值 | 当作"那一天"的作息塞进 `daily`，之后由真实数据滚动替换 |
| `lastActiveDate` 已经是几个月前 | 合成出来的日期照旧留着（那些日子**确实用过**）；只有使用日超过 21 个时才会挤掉最早的 |

迁移是**读盘时在内存里完成**的，磁盘上的文件要等下一次 `learnHabit`（下一次采样）
才被重写成 v2 —— 所以升级后看到文件还是 v1 格式是正常的。
确定性的验收在 `tools/acceptance.cjs`（三条：正常迁移 / 太旧的被裁 / 坏数据退回空画像），
真机确认在 `tools/probe-habit-model.cjs`。

**实测数据**：用户真实 `habits.json`（v1）里曾经存着 `other`（没认出来）的计数，
15 点那一格 `other=8` 甚至比 `browsing=6` 还多 —— 于是那句台词变成了
"……一般在其他（没认出来）……"。这就是 §5.2「当作没看见」那条规则的由来。
回归探针：`tools/probe-scene-unrecognized.cjs`。

### 2.2 L2 行为信号：`你已经连续 2 小时没起来了`

这层**不落盘**，每次采样时现算（`buildBehaviorSnapshot()`）：

| 字段 | 来源 | 阈值 |
|---|---|---|
| `idleSeconds` | `powerMonitor.getSystemIdleTime()` | — |
| `sessionMinutes` | 距 `sessionStartedAt` | 锁屏/休眠、以及空闲 ≥600s 都会重置会话（"离开过"就不算连续使用） |
| `switchesLastHour` | 最近一小时观察里**场景变化的次数** | ≥8 次算"注意力分散" |
| `userState` | `inferUserState()` | `away`(没动 ≥300s) / `idle`(≥120s) / `shallow`(切换 ≥8) / `deep` |
| `lateNight` | `isLateNight(hour, lateNightHour)` | 默认 1:00–5:00 |
| `hour` | 本地小时 | — |

⚠️ `switchesLastHour` 是**粗粒度**的：采样间隔默认 30 秒，所以它衡量的是
"半小时里换了多少个不同场景"，不是真实的窗口切换次数。文档与代码注释里都写明了这一点，
不要把它当精确的焦点日志用。

### 2.3 L3 长期事实：`你一般 1 点睡`

**8 类 key**（`MemoryFactKey`）：`name / interest / routine / activity / project / preference / relation / note`。
与"习惯"最相关的是：

| key | 规则抽取（`extractFactsHeuristic`） | 置信度 |
|---|---|---|
| `routine` | `我(一般\|通常\|每天\|平时)? (数字+点(半)?(睡\|睡觉\|起床\|起\|下班\|上班))` | 0.70 |
| `activity` | `我(今天\|昨天\|刚刚…) (写代码\|debug\|开会\|上课\|考试\|健身…)` | 0.60 |
| `project` | `我(最近\|正在\|打算…)?(写\|做\|搞\|训练\|开发) X` | 0.65 |
| `interest` / `preference` | `我(很)?(喜欢\|爱好\|迷上) X` / `我(不喜欢\|讨厌) X` | 0.60 |
| `name` | `我叫\|我的名字是\|叫我 X`（只认这三种明确说法） | 0.80 |

两条写入路径**互为兜底**：

1. **规则**：每轮对话后立刻跑（不联网、零成本、永远可用）；
2. **模型**：每 `consolidateEvery`（默认 **6**）轮整理一次，让模型输出 JSON 事实数组，
   能理解"我最近在鼓捣一个桌宠"这种没有固定句式的表达（置信度默认 0.9）。

**合并与淘汰**（`mergeFacts()`）：同 `key` + 同值 → `hits += 1`、置信度取高；
`name` 是唯一键，可被更高置信度覆盖；超过 **200 条**时按
`confidence × min(5, hits)` 淘汰最弱的。

**读取**：`buildContext(query)` 打分 = `bigram 命中数 × 2 + confidence × min(5,hits)`，
取前 6 条进聊天提示词；日记取前 10 条。`routine` 目前**只用来让她说话更贴**，
不参与任何行为判定（见 §8 已知限制）。

### 2.4 L4 反馈 → 反思 → 策略：唯一会"改行为"的一层

这是整个习惯学习里**唯一反向影响当下行为**的闭环，也是"她因为我没回应而变安静"的落点。

```text
她主动开口 ──> feedback-*.jsonl（记一条：时间 / 场景 / 说了什么）
    │
    └─ 3 分钟内主人有任何互动或对话 ──> 标记 responded = true
                    │
       每天 reflectionHour（默认 23）后写一次反思（启动补昨天）
       输入 = 反馈统计 + 当天对话轮数 + 心情曲线 + 场景分布
       输出 = 反思正文 + 洞见（insights）
                    │
              applyInsights() ──> policy.json（乘数只能 ≤1）
                    │
        effectivePerception() ──> 频率闸门（最小间隔 / 每小时上限 / 按场景系数）
```

判定窗口是 **`RESPONSE_WINDOW_MS = 3 分钟`**。文件格式是"每条开口写一行 JSONL"，
而**读的时候按 `时间|文本` 去重、后写的覆盖先写的**：所以开口时先落一条
`responded: false`，真的被回应了再补一条 `responded: true` ——
不必回头改文件，也不会把同一次开口算成两次（这一点很容易写错，`growth-store.readFeedback()`
的 `Map` 去重就是为此存在的）。

**洞见是怎么来的**（两条路，互为兜底）：

| 路径 | 规则 |
|---|---|
| 模型 | 反思提示词要求输出 `{"insights":[{"scene":"coding","action":"quiet-down","reason":"…"}]}`；`action ∈ {quiet-down, keep, speak-up}`；**没有把握就给 `[]`** |
| 本地（`heuristicInsights`） | 某场景 `total ≥ 3` 且回应率 `≤ 1/3` → `quiet-down`；`total ≥ 5` 且回应率 `≥ 0.8` → `speak-up`；全局 `≥ 6` 次且回应率 `≤ 0.25` → 全局 `quiet-down` |

**乘数方向很关键**（`applyInsights` + `clampOverlay`）：
`quiet-down` → ×0.5（间隔随之翻倍）；`speak-up` → ×2 但被夹在 ≤1，
也就是"**最多回到用户设定**，绝不会比用户设的更频繁"；所有乘数夹在
`[POLICY_MIN_FACTOR = 0.25, 1]` 之间 —— **只能收紧**。

**生效方式**（`effectivePerception()`）：用户设"最小间隔 10 分钟"，她学出
"写代码时少打扰"（场景系数 0.5），那么写代码时实际间隔 = 10 / 0.5 = **20 分钟**。
她**不改用户配置**，只在用户配置之内收紧。

**可审计、可回退**：每次调整都写进 `reflection/policy-log.md`；
设置面板「成长与反思」里有「重置策略」按钮（二次确认），托盘/右键菜单也有入口；
关掉 `policyAdapt` 开关会把策略立刻重置回中性。

### 2.5 L5 经历与时间线：`今天你写代码花了 2 小时 22 分`

**时间线**（`shared/timeline.ts`）：每次已识别的观察并入当天的活动段 ——
**scene 相同 + 间隔 ≤ 150 秒**就延长上一段，否则另起一段；换段时把上一段**补到当前时刻**。
"没认出来"（`other`）不写进时间线，但在**同一个进程**内会被桥接（延长上一段并记
`unrecognizedSamples`）—— 否则夹一次没认出来就会把同一个应用的连续使用切成碎片
（用户实测：`10:58–11:01 聊天`、`11:03–11:05 聊天`…）。阈值与桥接口径见
[`timeline-continuity.md`](timeline-continuity.md)。
`summarizeDay()` 汇总出 `activeMinutes / idleMinutes / unaccountedMinutes / byScene / byApp`，
`formatTimelineText()` 渲染成给提示词与界面用的一段话，
`narrateTimeline()` 还能让模型写一段"她记得的今天"落进 `daily-<日期>.md`。

**三条规则都是被真实数据逼出来的**（用户实测："PVZ 一个程序被拆成十几行，时长是不是算错了？"）：

| 规则 | 为什么 |
|---|---|
| 合并键**只有 scene**，app 只作段内的代表性标签 | 同一个程序在不同时刻会被读成不同字符串（`PVZ Universe` / `Plants Vs. Zombies Universe` / `植物大战僵尸 Universe`）。拿 app 当合并键 → 一段被切成十几段、每段时长接近 0、`byApp` 列成三行。实测某天 **93 处 / 67.5 分钟**的连续活动被这样拆散 |
| 换段时把上一段的 `end` **补到当前观察时刻** | 采样是 30 秒一次，真实切换点落在两次观察之间。旧实现让那 30–90 秒**两边都不算**（实测 **136 处 / 111.9 分钟**凭空消失） |
| `unaccountedMinutes` = 跨度 − 活动 − 空闲 | 差额全是"没认出来"（按需求当作没看见）与"没采样"。以前这个数根本不存在，于是"在线 8 小时、活动 23 分钟"看起来就像统计错了 |
| 应用**身份**用**进程名**（`observation.app`），模型给的名字放 `appLabel` | 模型读的是窗口标题，会随界面语言/场景变；进程名不会。实测验收里出现过模型说"Code"、真实前台其实是 `typora` —— 身份错了，时间线与习惯统计就全是散的。界面显示优先用 `appLabel`（说人话），分组统计一律用身份（稳定） |

**实测（用户真实数据，同一天同一份观察记录，旧规则 → 新规则）**：

```
段数        392 → 283      （<1 分钟的碎片 360 → 164）
在电脑前    23.5 → 113.5 分钟
离开/没动   30   → 119.8 分钟
没认出来/没采样            415.3 分钟（跨度 646 分钟，三项相加自洽）
```

`byApp` 也改成**按段内占比分摊**（原来"一段属于一个 app"），这样
`sum(byApp) == activeMinutes` —— 面板上两处数字对不上是最招人怀疑的。

**旧数据可以修**：时间线是增量聚合出来的，规则改了历史文件不会自动跟着变。
`node tools/rebuild-timeline.mjs [日期] [--dry]` 会用**产品里的同一份纯函数**
重放 `observations-<日期>.jsonl` 并重写 `timeline-<日期>.json`
（观察记录是原始数据、绝不被改动；`narrative` 保持原样）。

**记忆宫殿里的习惯节点**（`suggestNodes()`，反思时跑）：
`habitSamples ≥ 20` 且某个场景的采样 `≥ 10` → 生成一条
`常常在写代码` 的 `habit` 节点。这类节点**特意被排除在"最近的事"之外**
（`recentMomentForSmallTalk()` 跳过 `first-meet` 与 `habit`）——
它由"习惯询问"那一档负责，不该再被当成一件"最近发生的事"重复提起。

### 2.6 L6 习惯模型：`她眼里的你`（会调用大模型）

L1 的产物是**数字**（"工作日 10:00 写代码 6 天"）。L6 把它**归纳成一段人话**，
让她能说、也让你能看懂她到底学到了什么。落在 `perception/habit-model.json`：

```jsonc
{
  "summary": "你工作日早上一般在写代码，下午会看点东西。",   // 2~4 句，她视角
  "line": "这个点你一般在写代码吧？",                        // 一句能直接说出口的话
  "routines": [                                            // ← 本地算的，不是模型写的
    { "when": "工作日 09:00–11:00", "what": "写代码", "app": "Code", "days": 6 }
  ],
  "source": "llm",            // llm = 大模型写的措辞；template = 本地模板兜底
  "tokens": 412,
  "updatedAt": "2026-09-26T22:03:00.000Z",
  "samples": 412, "activeDays": 15,
  "error": ""                 // source=template 时写明为什么（面板会显示）
}
```

**分工是这一层最重要的设计决定**：

| 部分 | 谁来做 | 为什么 |
|---|---|---|
| `routines`（几点、在做什么、用什么、**几天**） | **本地纯函数** `buildHabitRoutines()` | 这些是事实，必须能从 `habits.json` 逐条复算出来；让模型生成数字就等于允许它编 |
| `summary` / `line`（措辞） | **大模型**（可用时） | 模型擅长的是把表格写成自然语言，而不是记住"6 天" |

也就是说：**模型只写措辞，不写事实**。模型不可用 / 调用失败 / 输出解析不出来时，
退回 `localHabitModel()` 的模板，并把原因写进 `error` ——
面板永远有东西看，功能不会静默消失。

**触发时机**：

1. **每天一次**：`habitModelHour`（默认 22 点）之后的第一次采样 —— 与"每天第一次采样清理明细"
   同一个模式（复用感知自己的心跳，不额外起定时器）；
2. **手动**：设置面板「习惯模型」→「立刻建模」（`force` 会绕过"样本没涨就跳过"）。

**三条克制**：

- **样本没涨就不重复调用**（`lastModelSamples`）—— 结论不会变，白烧 token；
- **输入是统计文本**（`habitStatsLines()` + 条目），不是原始 JSON、更不是截图 ——
  提示词里明确要求"只能使用下面出现过的事实，不要编"；
- **输出不改变任何行为**：不改频率、不改触发、不改提示词权重。它只被**展示**与
  用作闲聊里的一句话（`line`）。

**token 记账**：这次调用会经 `AIService.recordUsage()` 记进 AI 预算 ——
她"自己想做的事"不该悄悄烧掉额度而账面上看不出来。
（视觉理解与每日反思**还没接**这条，见 §8.10。）

**一句话怎么被用出去**：`buildSmallTalkFor()` 会先用 `habitPredictionText()` 判断
"此刻有没有可说的习惯"（避免凌晨三点说"这个点你一般在写代码"），
成立才轮到模型那句 `line` 顶上；没有模型时就是模板句
（`按你平时的习惯，这个点一般在写代码，今天也是吗？`）。

## 4. 她怎么把这些用出来（四个出口）

| 出口 | 用到哪几层 | 具体形态 |
|---|---|---|
| **闲聊小话头** | L1 + L5 | 一次开口机会里轮换 5 种候选（需求里归纳成 4 类）：最近的事 > 今天的活动 > 习惯询问 > 问候 > 陪伴自语；`pickSmallTalk` 避开上一次说过的类别 |
| **只换姿势不开口** | L1 | 场景连续稳定 **90 秒**（且不在频繁切换中、距上次触发 ≥20 分钟）→ 演 `work`（coding/writing/terminal）或 `read`（reading）；**不占"每小时打扰上限"** |
| **提醒** | L2（+ 情绪） | 久坐 `sessionMinutes ≥ 120` 且 `idleSeconds < 120`；深夜；饱腹 ≤40；心情 ≤25 |
| **提示词** | L3 + L5 | 聊天带上`【你记得的事】`与`【主人今天在做什么】`；日记带上事实前 10 条与时间线 |

闲聊小话头是 L1 **唯一会说出口**的地方（设置面板的「这个点通常」等读数里也会展示它，
但那只是给你看的数字，不是"她开口"），
且它**不新增开口机会** ——
频率完全由 `gateIntervention`（免打扰时段 / 最小间隔 / 每小时上限 / 用户不在）决定，
只是把原来那句固定的"习惯询问"换成一组轮换内容（需求："频率不变"）。

> 顺带说明：`isPlanEnabled('small-talk')` 只要求 `behavior || habits` **任一**开着，
> 因为它的一组候选里既有"习惯询问"（归属 `habits`）也有问候/今天的活动（归属 `behavior`）；
> 真正决定某一类能不能进候选的是 `buildSmallTalkFor()`：习惯询问只在 `habits` 开着时才进候选。

## 5. 三个"明确不学"的边界

### 5.1 不猜
规则抽取的置信度不足就丢掉 —— 注释里的原话是"**记错了比没记住更伤陪伴感**"
（她会一本正经地说错你的事）。模型路径同样要求"只写明确说过的"，且提示词里
写了"没有把握就给 `[]`"。

### 5.2 没认出来 = 当作没看见
用户原话：『如果是没认出来，就当作没看见，不应该在宠物对话的时候说出
"这个时候经常在说不清"这种话』。这一条在**五处**同时成立，缺一处就会漏：

| 位置 | 做法 |
|---|---|
| `learnHabit` | `other` 不写入画像 |
| `topSceneAtHour` | 遍历时跳过 `other`（**救旧数据**：文件里已经存着计数） |
| `appendObservation` | `other` 不建段、也不打断上一段（否则"今天在做什么"里会出现"上午在其他"） |
| `habitPredictionText` | 取到的场景若不可识别则不开口 |
| `localObservationFromWindow` | 认不出来干脆不记（比"记一条 other"更干脆） |

### 5.3 不改用户设置，只能收紧
L4 的乘数夹在 `[0.25, 1]`，`speak-up` 最多回到用户设定。
"她变得更安静"是她学的，"她变得更吵"不是 —— 那是用户该决定的事。

## 6. 存储与保留

| 数据 | 位置 | 保留 | 机制 |
|---|---|---|---|
| 习惯画像 | `perception/habits.json` | **不按天清理**（聚合画像，很小） | 「清空感知数据」一键清空 |
| 观察明细 | `perception/observations-*.jsonl` | `retentionDays`（默认 90 天） | 过期先压成 `archive/<月>.md` 一行再删 |
| 时间线与当日叙述 | `perception/timeline-*.json`、`daily-*.md` | 同上 | 同上 |
| 长期事实 | `memory/profile.json` | 不清理（最多 200 条按分数淘汰） | `mergeFacts` |
| 反馈流水 | `reflection/feedback-*.jsonl` | `keepReflectionDays`（默认 180 天） | 启动时 `pruneReflections` |
| 策略 | `reflection/policy.json` + `policy-log.md` | 不清理（很小，且要可审计） | 「重置策略」 |
| 宫殿习惯节点 | `memory/nodes.json` + `palace.md` | 超 `palaceCompressMonths` 折叠归档 | — |

数据目录默认在**项目目录的 `<appRoot>/data/`**（不在 C 盘），详见 `docs/memory.md` §2。

一键清空（`observation-store.clear()`）会：把 `perception/` 下除 `perception-log.md` 外的
文件全部清空，删掉 `habit-model.json`，并把 `habits.json` 重置为空画像 ——
也就是"她重新开始认识你"。

## 7. 用户能控制什么

| 开关 / 设置 | 位置 | 作用（关掉/改小之后） |
|---|---|---|
| **习惯学习**（`habits`） | 感知面板 | 关掉：不再积累时段统计（也没有"按你的习惯…"这类台词），习惯模型也不再重建 |
| **行为观察**（`behavior`） | 感知面板 | 关掉：不再统计空闲/连续使用/切换频率，久坐与深夜提醒失效 |
| 采样间隔 / 截图宽度 | 感知面板 | 决定 L1、L5 的时间分辨率（越密越准、越费 token） |
| 免打扰时段（默认 23:00–8:00） | 感知面板 | 这段时间内一律不主动出声 |
| 最小开口间隔（默认 10 分钟）/ 每小时上限（默认 4 次） | 感知面板 | L4 **只能在这个上界之内**收紧 |
| 久坐阈值（默认 120 分钟）/ 深夜起点（默认 1:00） | 感知面板 | 决定 L2 的两条提醒什么时候来 |
| **习惯建模时刻**（默认 22 点） | 感知面板 | 每天到这个点之后建模一次；「立刻建模」按钮可随时手动触发 |
| **场景纠正**（每行 `关键词=场景`） | 感知面板 | 模型稳定判错时由你说了算（默认带 `Chrome=browsing`、`Edge=browsing`） |
| 允许反思调整行为策略（`policyAdapt`） | 成长面板 | 关掉 = 只写反思、不动行为（并立刻把策略重置回中性） |
| 保留天数 / 「清空感知数据」 | 感知面板 | 见 §6 |

## 8. 已知限制与可整理项（按优先级）

> 这一节是**诚实清单**：以下都不是 bug，但值得知道。
> ✅ = 已在"习惯建模"这一轮修掉。

### ✅ 8.1 样本门槛偏低，"平时"可能只是"刚才两次"
原来 `topSceneAtHour` 默认 `minSamples = 2`，**两个采样（约 1 分钟）**就足以让她说
"按你平时的习惯，这个点一般在写代码"。

**已修**：计数单位改成**天**（同一天同一小时同一场景只记一次），门槛提到
**该小时 ≥3 天、主场景 ≥2 天**（`HABIT_MIN_DAYS` / `HABIT_MIN_SCENE_DAYS`）。
现在最快也要 3 个不同日子才会开口 —— "平时"这个词终于站得住。

### ✅ 8.2 没有遗忘 / 衰减，作息变了要等新数据淹没旧的
原来 `hours` 是纯累计计数，三个月前的 10 点和昨天的 10 点权重完全一样。

**已修**：改成**滑动窗口** —— 桶里存的是"哪几天看到了这个场景"，
只保留最近 `HABIT_WINDOW_DAYS`（21）个**运行过的日子**。天数永远是整数，遗忘就是窗口滑动。
窗口的单位是"**使用日**"而不是日历天：没启动程序的日子不占名额，所以时间流逝本身不会让她忘掉你。
> 中途试过指数衰减（×0.95/天），但"连续 3 天"的权重会变成 2.85，
> **按"天"表达的门槛全被它搞错**，而且小数天数没法解释 —— 所以换成了窗口。

### ✅ 8.3 `latestActiveHour` 只增不减
原来它是历史上"最晚有活动的整点"的最大值，一旦学到 23 就再也不回落。

**已修**：改成**最近 21 天（`HABIT_WINDOW_DAYS`）的中位数**（`daily` 滚动窗口）。
好处是既抗单日异常、又会跟着作息移动：连续几周早睡之后，"通常几点还在"自己就降到 21 点了。

### ✅ 8.4 不区分工作日 / 周末，也不看应用
原来画像只有 `小时 × 场景` 两维，周六 10 点和周三 10 点是同一格，`Code` 与 `Typora` 也不分。

**已修**：桶 key 变成 `weekday|hour` / `weekend|hour`；`apps` 单独记每个桶里用得最多的应用。
台词与统计文本里都会带上应用（`这个点一般在写代码（Code）`），前提是**应用也攒够天数**。
旧数据落在 `*` 档，读数时会写明"平时"而不是冒充工作日/周末。

### 🟡 8.5 习惯模型每天只更新一次
`summary` 是快照：白天学到的新习惯要等到 `habitModelHour`（默认 22 点）之后，
或者你手动点「立刻建模」。→ 面板上有按钮，暂时够用；想更"实时"就得加重建节流。

### 🟢 8.6 切换次数是粗粒度的
30 秒采样决定 `switchesLastHour` 的上限是"每小时约 120 次"，实际能测到的远低于真实窗口切换。
它只被用来把 `userState` 分成"深/浅"，不该拿去做更强的判断。

### 🟢 8.7 L3 的 `routine` 只有一条正则，且不参与行为
`我一般 1 点睡` 能抽到，但"我最近都两点才睡"抽不到；
而且 `routine` 目前只影响她**怎么说话**，不影响任何触发（真正管深夜的是 L2 的 `lateNightHour`）。
两处"作息"概念并存，容易让人误以为改了 `routine` 就会改提醒时间。

### 🟢 8.8 L1 与 L5 是两套并行统计
`habits.json`（按天的小时直方图）与 `timeline-*.json`（活动段）都在描述"你在做什么"，
前者永久保留、后者 90 天过期，两者的"场景集合"口径也不完全一样
（都过滤 `other`，但对 `idle` 的处理不同：习惯跳过 idle，时间线**保留** idle 段用于算空闲时长）。
→ 可以合并成一份"按天按小时"的聚合，但会让"今天在做什么"的实时性变复杂。

### 🟢 8.9 不可识别的判定分散
`isRecognizedScene()` 只排除 `other`；`idle` / `sensitive` 是各自在
`learnHabit` 里单独跳过的。也就是说"什么算没看见"这件事有两个入口，
将来加新场景（例如 `unknown`）容易只改一处。→ 可以收敛成一个 `shouldLearn(scene)` 纯函数。

### ✅ 8.10 只有部分调用记了 token
以前只有 `AIService` 自己发的请求会 `addUsage`：**视觉理解**（每分钟一次！）与
**每日反思**的 token 从来没进过预算，面板上的数字一直偏乐观。

**已修**：记账下沉到 `LLMClient`（所有大模型请求的**唯一出口**）——
它每次成功调用都回调 `onUsage`，再由 `AIService.recordUsage()` 记两本账：

| 账 | 含义 |
|---|---|
| `budget.used` | **持久化**的累计（跨重启），用户的 token 预算按它算 |
| `sessionTokens` / `sessionUsage` | **本次运行**的用量，并按用途分档（聊天 / 看屏幕 / 反思 / 习惯建模…） |

于是"她这一次开着花了多少、花在哪"在设置面板的「本次运行」那一行直接能看。
调用点不需要（也不应该）自己记账 —— 那样会重复计数，代码里已经不允许再出现 `addUsage`。
新增调用点时顺手写一个 `purpose`（`LLMPurpose`），面板与日志才知道钱花在哪。

### 🟢 8.11 `IDLE_THRESHOLDS.sessionBreak` 定义了却没人用
重置会话用的是**内联字面量 `600`**（`perception-service.ts` 的采样循环），
常量本身没有任何引用。两处数值目前恰好相等，但改一处不会影响另一处。

### 🟢 8.12 习惯建模要求「对话」开关是开的
`evaluateAIUsability()` 把 `chat` 当成"能不能用大模型"的总闸（视觉理解也一样）。
所以关掉「对话」但留着「习惯学习」时，建模会退回本地模板并写明原因。
语义上"建模"不属于对话，将来可以把这道闸拆开（例如 `enabled && (chat || perception)`）。

## 9. 出错时怎么排查

| 现象 | 先看哪里 |
|---|---|
| 她说了"按你平时的习惯…"，但内容不对 | 设置面板的「习惯画像（3.6）」三个读数：`学到了`（采样/活跃天/最近窗口）与`这个点通常`（会标明按工作日还是周末）；再打开 `perception/habits.json` 看那一小时的分布 |
| 面板上的"习惯模型"一直是本地模板 | 看那段话下面的小字（`source` + 原因）：没配密钥 / 关掉了「对话」开关 / 接口报错都会写明 |
| 习惯模型里没有条目 | 条目要求**同一时段 ≥3 天**才会出现；刚装第一天只会有"还没摸清"。也可以点「立刻建模」试 |
| 她老是说同一句 | `perception-log.md` 里 `开口（small-talk）：…`（习惯询问现在由"日常闲聊"这一档说出，所以 kind 是 `small-talk` 而不是 `habit`）；再确认候选是否齐全（`pickSmallTalk` 靠"避开上一类"来轮换） |
| 她变安静了 / 变吵了 | 成长面板 §4.2 的「当前策略」表格 + `reflection/policy-log.md`（每次调整都写了原因） |
| 没配密钥时习惯完全不涨 | 确认「习惯学习」与「用窗口信息辅助判断」都开着 —— 本地降级靠窗口上下文，终端短路也受那个开关约束 |
| 她提的场景明显是错的 | 感知面板的「场景纠正」：加一行 `关键词=场景` |
| 换了作息但她还在说旧的 | 这是**设计如此**：衰减半衰期约 13.5 天。想立刻清空就点「清空感知数据」 |
